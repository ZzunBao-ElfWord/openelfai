# 豆包真实视频首播失败调查（2026-11-02）

## 结论

10月30日两次真实安卓播放失败存在同一链路：读取位于文件尾部的MP4索引时等待约8秒，客户端断开（CDN记499、传输0字节）；后续播放器从先前媒体数据位置21722重试，而非索引目标位置，错误按MP4 box解析媒体码流，产生偏移808474614，随后CDN正确返回416。

本次只读分析，不是修复或真机故障注入验收。未修改代码、环境、缓存、原视频、数据库、签名或安装包。

## 字节级对照

- 246b2da3文件实际大小4,836,772字节，82eb4264文件7,890,376字节。
- 真实媒体数据始于21722。对两个文件读取21722至22405的684字节，若错误当作MP4 box序列解析：首box大小668，下一个位置22390；下一个误读大小808452224；相加得到808474614，与两次实际失败Range精确一致。
- 这表明请求不是用户拖动到771MiB，也不是视频本来这么大；是解析状态与重试位置不匹配的结果。
- 正常尾部请求在后续缓存可用时返回206；缓存下载快不代表首次冷请求没有超时。

## 播放器源码佐证

Build22此前模拟器日志标记AndroidXMedia3/1.9.2。该版本ProgressiveMediaPeriod.ExtractingLoadable.load在dataSource.open异常时，会在finally中从前一次extractor input读取位置覆盖positionHolder；新input只在open成功后的init中建立。这与官方已修复问题#3440描述的陈旧位置重试机制相同。

官方问题及修复：https://github.com/androidx/media/issues/3440
当前所用版本源码：https://raw.githubusercontent.com/androidx/media/1.9.2/libraries/exoplayer/src/main/java/androidx/media3/exoplayer/source/ProgressiveMediaPeriod.java

## 修复建议与验收

1. 安卓端升级到包含对应修复且经验证的播放器版本，或限范围补入官方修复；不可仅吞掉416或无上限重试。先做“尾部open超时一次后恢复”的故障注入回归，确认重试仍指向原目标而非21722。
2. 客户端补充安全诊断与过期回调隔离，避免旧controller报错覆盖新视频状态。仅记录公开素材路径与位置，不记录登录令牌。
3. 索引前置/预热用于减少冷请求等待，但不代替重试错误修复。不能无检查重封装原视频导致AI来源/UUID元数据丢失；保留原文件，独立验证后再引入新文件名/缓存策略。
4. 原计划按版本规则递增；用户随后明确要求本次测试重包不递增，因此另生成1.0.4 Build22独立测试APK，保留原Build22。见下方实施记录。
5. 之前发现的源站越界Range错误返回206最后1字节，是独立协议缺陷，不是本次CDN拒绝808474614这一越界请求的直接错误。不能将其当作本次416已定位的替代根因，不能取消CDN范围校验。
6. 验收需包括：同一视频冷启动、温缓存、尾部读取超时恢复、连续切换与拖动。不得以HEAD200、首段206或1MB测速代替实际播放通过。
