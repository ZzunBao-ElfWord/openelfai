# 收益修复：本地实现，尚未部署

## 改动

- 新打赏收益记录付款人、AI 与金额；各 AI 只展示本账号从该 AI 获得的收益，不再重复展示账号总收益。
- 待结算记录改为稳定主键游标扫描，避免最新500笔挤掉到期旧记录；结算仍由收益快照/提现触发。
- 提现申请和批准出款均重新检查退款欠额、支付宝待核对交易及收益付款来源风险。
- 退款在原事务内保留来源风险标记；重复退款不会重复处理；补充值不自动清除来源风险。
- 不自动扣减收款创作者的历史余额或已提现金额。风险冻结指阻止该创作者新提现及待审核提现的批准，并非改写余额。
- 已提交给支付机构的付款仍按原订单查证，不能因为后来出现退款就当作没有付款。
- 客户端手续费预估与服务端一致，按分四舍五入。
- 新增内部核对 API 和本机运维工具；没有自动批准出款，没有部署定时任务。

## 必须知悉的限制

当前钻石钱包是混合余额，没有逐充值订单的消费批次归因。因此退款标记采用保守的付款人级风险保护，可能影响该付款人关联的其他创作者收益，须人工查证，不代表每笔收益都来自被退款订单。

旧收益没有付款人字段：不补造、不清零，提现暂挂，需核对真实支付/打赏/退款流水后才可手动放行。人工放行匹配当前旧记录指纹，记录依据和审计信息；新记录出现后旧放行失效。不得为绕过提示而直接全部放行。

不能自动追回已出款资金。本次没有实现逐订单自动追偿、税款计算或商户资质校验。

旧 AI 收益 refId 可用于按 AI 汇总；缺失或无法归属的历史记录仍保留在账号总收益，不伪造某只 AI 的收益。AI 转赠不转移原主人的已得收益。

## 运维

工具：server/scripts/earnings-ops.cjs，仅连接服务器本机127.0.0.1:8787。需要现有环境文件中的 WITHDRAW_REVIEW_TOKEN，不要把令牌放命令行或发到客户端。

帮助（无请求）：`node server/scripts/earnings-ops.cjs --help`。

服务器部署后使用 `node --env-file=/etc/openelf-api.env /实际工具路径/earnings-ops.cjs list` 查看队列；`list --status pending_reconciliation` 查看异常待查证队列；`risk 用户ID` 查看退款风险和历史记录指纹。

批准、拒绝、查单、风险放行均须显式 --confirm；批准还须 --payee-verified 和审核依据，可能真实付款。运维人员在真实核实后自行操作，不能为“测试”批准真实出款。

生产服务器未配置令牌时内部入口保持关闭。前端永远不获取该令牌。
